# Covenant contracts

These Arkade Script sources are the **authoritative specification** of Arkade Heroes' game actions. Every on-chain action the server performs today is shaped to satisfy these covenants, so switching enforcement from "server promises + client audit" to "emulator co-signing" changes *who refuses an invalid transaction*, never the transactions themselves.

| Contract | Governs | Modeled on |
|---|---|---|
| `arkade_heroes.ark` | Hero breeding (parents retained, child fresh-minted with oracle-attested genome) and transfer | `arkade-os/compiler` `examples/arkade_kitties.ark` (compiled baseline) |
| `wager_escrow.ark` | Wagered matches: atomic two-stake settle to the winner, time-locked forfeit/refund | `ArkLabsHQ/coinflip` escrow taptree (`docs/PROTOCOL.md`) |
| `item_offer.ark` | Non-interactive item sales (pay-seller-in-same-tx), reusable for player-to-player trading | `arkade-os/banco` offer covenant |

## How they bind (enforcement model)

Covenant leaves are ordinary multisigs where the emulator's key is **tweaked by the script hash**:

```
scriptHash = tagged_hash("ArkScriptHash", script)
tweakedKey = emulatorKey + scriptHash·G
```

The script bytecode itself travels in an **Emulator Packet** (TLV `0x01` inside the ARK extension OP_RETURN). The emulator (regtest: `http://localhost:7073`) runs the script in its Arkade VM and produces its signature **only if the predicate holds** — the signature is the proof. The C# primitives for this are the SDK's, in `NArk.Arkade` (`ArkadeTweak`, `EmulatorPacket`, `EmulatorClient`, `ArkadePsbtExtensions`); the game keeps only the composition on top of them, in `src/ArkadeHeroes.Chain/Covenants/`.

## Status

- **All three contracts compile** with `arkade-os/compiler` (`arkadec`); artifacts are committed under `contracts/build/`. Rebuild: `arkadec contracts/<name>.ark -o contracts/build/<name>.json`. The `uint64le` vs `scriptnum` implicit-conversion warnings match the compiler's own shipped kitties example.
- **The enforcement pipeline is proven on regtest** (`CovenantSpendTests` + `CovenantProbe`): covenant VTXO (script-tweaked emulator key + operator key leaf) funded from a self-custody wallet, spent through the emulator with the packet attached — passing script co-signed, failing script refused.
- **The first game covenant is live** (`OfferFulfillCovenantTests` + `ArkadeArtifactContract`/`ArkadeCovenants.PayTo`): a resting offer VTXO fulfillable by anyone who pays the seller the exact ask in the same tx — underpayment refused by the emulator, honest fulfillment co-signed; the taker needs no prior funds and no seller interaction. This is the banco pattern the item marketplace builds on.
- **The item marketplace is live — buyer-funded, covenant-enforced** (`CovenantOfferProbeTests` + `OfferContracts`/`OfferFulfillFlow`/`OfferReclaimFlow`): a seller rests ONE item-asset unit behind an offer covenant with a `fulfill` leaf (`PayTo(seller, ask)`) and a timelocked `reclaim` leaf (`RefundTo(seller, offerValue)`, the task-17/18 refund machinery). Unlike the sats-only probe above (where the taker keeps the offer VTXO's own spread), ANY buyer funds the ask from their OWN wallet: `CovenantSpender.SpendManyAsync` gained a `fundingCoins` param so the actor's plain coins ride the covenant spend — the emulator co-signs only the covenant input while the buyer signs their own funding inputs. Proven live: honest fulfil, **underpayment refused**, **multi-funding-coin** (the per-coin re-sign loop), **seller reclaim after expiry** (asset passthrough returns the item, same MTP-gate + submit-once discipline as the wager refund), and **a whole unique supply-1 asset** (the hero shape). Server is the discovery index only; the buyer rebuilds the offer covenant locally from `GET /api/offers/{id}/params` and can verify the address before paying.
- **Hero sales reuse the SAME covenant** (`HeroSaleTests` + `CreateHeroOfferAsync`/`ClaimPurchasedHeroAsync`): the offer covenant only ever sees an asset id, so a HERO (a unique supply-1 asset) sells through the identical `fulfill`/`reclaim` machinery — no covenant change. The only hero-specific game logic is the buyer's post-fulfil claim: the server VERIFIES the chain shows the buyer holding the hero asset, then reassigns the record and strips its equipment (like `ConfirmTransferAsync`). Non-custodial throughout.
- **The wager escrow is live and fully oracle-authorized** (`WagerEscrowCovenantTests` + `ArkadeCovenants.{CheckSigFromStackGate,Sha256Gate,AtomicSweep,SettleAuthorized}`): two players stake into one escrow whose settle branches each pin (a) a per-branch settle message `SHA256("arkade-heroes-settle-v1|matchId|branch")` and the game oracle key via `OP_CHECKSIGFROMSTACK`, (b) the pre-committed server seed, and (c) the atomic both-stakes sweep paying the full pot to that branch's winner. Adversarial E2E: forged oracle signature refused, **cross-branch signature replay refused** (the `.ark` spec's branch-authorization requirement — closed), wrong seed refused, pot siphoning refused; the honest settle sweeps both stakes in one co-signed tx. The oracle key IS the receipt-signing game key, so the authorization players see on-chain matches the ProgressionReceipts they hold.
- **Per-party escrows + timelocked refunds are live** (`AbandonedStakeIsRefundableAfterExpiry_WithoutTheServer`): each player stakes into their OWN escrow contract (both carry both settle branches; each carries a `refund` leaf paying only its own party — coinflip's shape, forced by the no-pubkey-equality grammar limit). After expiry the staker reclaims with **no oracle, no counterparty, no game server** — pure covenant liveness. The E2E proves both the pre-expiry refusal and the post-expiry claim.
- **The refund is player-facing** (`ClientRefundFlowTests` + client `refund <matchId>`): the server publishes each covenant match's escrow params at `GET /api/matches/{id}/escrow`; the client REBUILDS the contracts locally via the shared `WagerEscrowContracts.Build` (server and client derive byte-identical addresses — asserted in the E2E), gates on the chain's median-time-past read from esplora (`EsploraChainTime`; endpoints advertised in `/api/chain/info`), and submits the canonical refund exactly once (`EscrowRefundFlow`; a pre-expiry call throws `RefundNotYetDueException` WITHOUT submitting, keeping the deterministic txid unpoisoned per invariant #4).
- **Timelock protocol invariants** (hard-won on arkd v0.9.9-rc.1 — every one of these produced a distinct live failure):
  1. **CLTV belongs on the TAPLEAF, not in the Arkade script.** arkd derives the canonical ark tx with locktime 0, so an arkade-script CLTV can never be satisfied (`ARK_TX_MISMATCH`). `ArkadeContractFunction.LockTime` wraps the leaf as `CompositeTapScript(LockTimeTapScript, NofN(tweakedKey))`.
  2. **The CHECKPOINT and the ARK tx must carry the SAME locktime** (each side's canonical form is derived from the other): checkpoint gets it from `ArkCoin.LockTime`; `CovenantSpender` rebuilds the ark tx PSBT to match (sequences `0xFFFFFFFE`). Mismatches surface as `CHECKPOINT_MISMATCH`/`ARK_TX_MISMATCH`.
  3. **arkd judges the leaf's CLTV against chain BLOCKTIME, not wall clock** (`FORFEIT_CLOSURE_LOCKED`). On a quiet regtest the chain clock lags badly — mine blocks until median-time-past ≥ expiry (consensus guarantees tip time > MTP, so MTP is sufficient under either semantic).
  4. **Submit timelocked spends exactly ONCE, after the chain clock passes expiry.** The canonical tx is fully deterministic (arkd rebuilds it: locktime = leaf CLTV, sequence `0xFFFFFFFE` — zero freedom), and arkd records a failure event under the submitted txid for every refusal. Its event replay treats the failed flag as **sticky** (`internal/core/domain/offchain_tx.go`: later `Requested`/`Accepted` events are ignored once `Failed` is set), so a refused-then-retried txid **finalizes at the RPC level but its VTXOs are never created** — the spend silently evaporates (and the input VTXO stays spendable: a double-spend hazard worth reporting upstream). Settle-type covenant spends are unaffected in practice: covenant violations are refused by the emulator BEFORE arkd ever sees a txid.
- **Wire-format trap (fixed)**: the Emulator Packet's INNER fields use Bitcoin CompactSize (`wire.WriteVarInt`), while NArk's `Extension`/`BufferWriter` varints are LEB128 (correct for the outer TLV). The encodings coincide below 128 and silently diverge above — surfaced as emulator-side "unexpected EOF"/garbage execution the moment settle scripts crossed 127 bytes. `EmulatorPacket` writes CompactSize internally; a unit vector pins it.
- **Buyer/actor-funded covenant-spend trap (fixed here, STILL LIVE UPSTREAM — re-verified 2026-09-05 at pin `b912bf9`)**: when a covenant spend ALSO carries the actor's own funding coins (the marketplace buyer paying the ask), NBitcoin's `TransactionBuilder` reorders the ark-tx inputs — the SDK's own comment says "may reorder inputs (e.g. by amount) even with ShuffleInputs=false", so the older "BIP69 outpoint" attribution in these notes was a guess at the mechanism, not the SDK's stated one — which triggers NArk's asset-vin remap (`TransactionHelpers.cs`) to rebuild the extension output from the ASSET packet ALONE, silently DROPPING the co-resident EmulatorPacket ("no emulator packet found"). **The remap also never remaps the EmulatorPacket's own `Vin`s, which are position-dependent in exactly the same way.** This now breaks the SDK's OWN covenant path (`AddArkadeEmulator` registers `ArkadeEmulatorPacketProvider`, whose packet the remap discards), so it is written up as a ready-to-file report at `docs/upstream/narK-extension-remap-drops-packets.md`. Our post-construction correction stays until it lands. The final input order is known only AFTER `ConstructArkTransaction`, so `CovenantSpender` corrects it post-construction: rebuild the extension with the EmulatorPacket's vins pointing at each covenant input's ACTUAL position (via its checkpoint's ark-tx index), read back NArk's already-remapped asset packet, then re-sign each funding input over the corrected outputs. The ark tx spends CHECKPOINT outputs, so each funding coin's internal checkpoint coin is reconstructed exactly as NArk does (`GenericArkContract([spendingScript, serverInfo.CheckpointTapScript])`) and signed; the funding CHECKPOINTS are buyer-signed too (the emulator verifies non-arkd sigs on ALL checkpoints, co-signing only the covenant inputs it finds in the packet).
- **Coin-selection includes recoverable coins (open, likely upstream)**: `SpendingService.GetAvailableCoins` (NArk `SpendingService.cs:168`) excludes only unconfirmed-onchain VTXOs, NOT recoverable (`Swept || Expired`) ones — so a recoverable coin can be offered to the auto-selector and doom a spend with `VTXO_RECOVERABLE`. Surfaces as a `SendAssetAsync` failure when depositing a treasury-bought item into an offer on an aged regtest. CONFIRMED mechanism; that a recoverable coin is actually present in that flow is inferred, not reproduced. The auto-selecting `Spend(outputs)` overload can't inject a filter; a fix wants `CanSpendOffchain`-filtering (cleanest upstream in `GetAvailableCoins`) or a settle/refresh before spend.
- **Artifact-format note (re-checked 2026-09-04 — the blocker moved)**: `arkadec`'s current JSON emission places function-arg tokens inline in `arkade.asm`, while the live emulator + ts-sdk (PR #319 program model) require covenant scripts to be **arg-free** (the tweak binds fixed bytes; args ride the EmulatorPacket witness as the VM's initial stack — `engine.SetStack`). Runtime covenants are therefore still authored as arg-free bytecode in `ArkadeCovenants` (coinflip's production approach), with the `.ark` sources as the semantic specification.

  **What changed**: the .NET SDK now ships the whole consuming half — `ArkadeArtifactParser`, `ArkadeProgramCompiler` (which resolves `$param` placeholders into arg-free leaves, exactly the missing step) and `ArkProgramContract`, which compiles a program artifact straight into a spendable contract. So the remaining blocker is only the **compiler's emission shape**. Verified by running the SDK parser over all three artifacts in `build/`: each fails with `The node must be of type 'JsonObject'` — the SDK expects the program model (`version`, `name`, `params`, `functions` as an OBJECT) while our pinned `arkadec` emits the CashScript-style shape (`contractName`, `constructorInputs`, `functions` as an ARRAY, and no `version` at all). Once `arkadec` emits the program model, the `.ark` sources can become the runtime source of truth via `ArkProgramContract` and the hand-rolled bytecode in `ArkadeCovenants` becomes a cross-check rather than the definition.
- The **transaction shapes** (asset groups, deltas, metadata hashes, output bindings) are live today — the NArk-backed server already produces them; these sources pin them down.
- **Grammar findings** (fixed in source, kept for the next contract author):
  - There is **no pubkey-equality predicate** (`pk == otherPk` doesn't parse in `require`). `wager_escrow` therefore settles branch-per-party (`settleToChallenger` / `settleToDefender`, `refundChallenger` / `refundDefender`) with the oracle co-signing only the true branch.
  - There is **no inline arithmetic** in comparisons (`value >= a + b` doesn't parse) — precompute as a constructor param (`potSats`). Both players see the params when funding (the escrow address commits to them), so this stays auditable.
- Oracle roles are interim: breeding/outcome oracles attest **deterministic, publicly recomputable** derivations (commit–reveal seeds are in asset metadata and API responses), so oracle misbehavior is detectable by anyone. The end-state replaces them with in-script derivation + VRF entropy per the ArkadeKitties design doc.
